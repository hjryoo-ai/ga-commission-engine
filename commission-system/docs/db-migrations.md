# DB 마이그레이션 번호 규칙

> E3.2(2026-10-09) 문서화. 결정 출처: ga-disclosure `docs/phase-03A-수용심사.md` §4-①(엔진 E3.1 질문 1에 대한 승인). 시험: `commission-infra` `MigrationNumberingTest`가 이 문서의 빈 번호 표를 읽어 실제 파일과 대조한다.

## 위치

| 디렉터리 | 적용 대상 | 내용 |
|---|---|---|
| `commission-infra/src/main/resources/db/migration` | H2(MODE=Oracle, 빠른 티어)와 Oracle | 공통 DDL·시드 |
| `commission-infra/src/main/resources/db/vendor/oracle` | Oracle만(앱 `spring.flyway.locations`, `OracleTestSupport`) | H2가 못 하는 요소 — `IS JSON`, 함수 기반 유일 인덱스, 파티셔닝, 트리거 |

Flyway는 두 디렉터리의 버전을 **하나의 순서**로 합쳐 적용한다. 디렉터리는 번호 공간을 나누지 않는다.

## 규칙

1. **번호는 전역 단조다.** 새 마이그레이션의 번호는 디렉터리와 상관없이 **두 디렉터리 전체의 최댓값 + 1**이다. 디렉터리별로 다시 세지 않는다(디렉터리별 대역 없음).
2. **번호를 다시 쓰지 않는다.** 한 번 쓴 번호는 다른 파일에 주지 않는다 — 지운 마이그레이션의 번호도 비워 둔다(지우는 일 자체가 아래 4에 걸린다).
3. **빈 번호를 만들지 않는다.** 새 번호는 최댓값 + 1뿐이다. 이미 있는 빈 번호(아래 표)는 채우지 않는다 — 채우면 그 번호보다 높은 버전이 이미 적용된 DB에서 "적용되지 않은 낮은 버전"이 된다.
4. **커밋된 마이그레이션은 고치지 않는다.** 정정은 새 번호의 마이그레이션으로 한다(ga-disclosure와 같은 원칙). 적용된 파일의 내용이 바뀌면 Flyway `validate`(운영 기동, 설계서 §12-8)가 체크섬 불일치로 실패한다.
5. **H2 겸용이 기본이다.** 공통 디렉터리 파일은 H2(MODE=Oracle)와 Oracle 19c+에서 같이 돌아야 한다. Oracle에만 되는 문장은 Oracle 전용 디렉터리에 두되 번호는 1의 규칙을 따른다.
6. **이름**: `V{번호}__{소문자_밑줄_설명}.sql`. 머리 주석에 Phase·근거(심사·지시 절)·이식성을 적는다.

## 이력 — 옛 규칙에서 생긴 순서 역전

옛 규칙에서는 공통 번호가 Oracle 전용 번호(V100~)보다 늘 낮았으므로, 전용 파일이 생긴 뒤 추가된 공통 파일은 "이미 적용된 높은 버전보다 낮은 버전"이었다. 운영 DB가 없던(가동 전) 시기라 실해는 없었고 파일은 고치지 않는다(규칙 4).

| 추가 순서 | 파일 | 추가 커밋 | 그 시점 Oracle 전용 최댓값 |
|---|---|---|---|
| 1 | V1~V10, V100·V101 | `5fc45d9`(Phase 0~12) | — |
| 2 | V11 | `f2e375b`(Phase 13) | V101 |
| 3 | V102 | `987d0c0`(Phase 14) | — |
| 4 | V12·V103 | `a4c4585`(E3) | V102 |
| 5 | V14, V13 | `ed00f37`·`c0142e0`(E3.1 — V14가 먼저 커밋됐다, 같은 PR) | V103 |
| 6 | V104 | E3.2 | V103 — 이 파일부터 규칙 1 |

이미 V103까지 적용된 DB에 V13·V14를 적용하려면 Flyway `outOfOrder`가 필요했다(E3.1 보고서 §5-6). V104부터는 필요 없다.
