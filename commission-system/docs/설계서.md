# GA 설계사 수수료 계산 시스템 설계서 — v1.2.2

> 목적: GA(법인보험대리점)에서 설계사 수수료를 계산·지급·환수·정산하는 핵심 시스템의 설계.
> 본 문서는 Claude Code에게 구현을 지시하기 위한 상위 설계 문서이며, 현재 코드베이스(`commission-system/`, **Phase 0~16 + E3 완료 — 룰 저장소부터 실행 가능 앱·비교설명 등급 API까지**·테스트 9,111건 통과: 단위/H2·앱스모크 8,994 + Oracle 통합 117 — v1.2.2부터 시드 고정 속성 테스트의 케이스를 개별 집계, Phase 16 기준 356건)와 **동기화된 버전**이다.
> **문서 관리 규약 (v1.1.5)**: 본 설계서의 단일 원본은 **코드 저장소**(`commission-system/docs/설계서.md`)이며, 각 Phase 완료 시 코드와 함께 갱신·리뷰한다. 저장소 밖 사본(대화 전달본 포함)은 파생본이다. `설계고찰.md`의 "반영 제안"은 설계서에 폴딩되는 즉시 반영 완료로 마킹한다.
> 기술 전제: Java 21 + Spring Boot + Oracle (도메인 코어는 DB 무의존).
>
> **면책(학습·포트폴리오)**: 본 문서의 규제 내용(1200%룰·분급제·비교공시 등)은 공개 감독규정을 기반으로 한 예시적 정리이며, 시행일·세부 기준·유권해석은 계속 갱신된다 — **실제 적용은 금융위원회·금융감독원 원문과 유권해석을 따라야 한다.** 문서에 등장하는 모든 요율·금액·수치·보험사·상품·설계사는 **가상의 예시값**이다.

## 0. 설계의 대전제

이 시스템의 최대 리스크는 기술이 아니라 **규정의 변동성**이다. 금융당국이 감독규정·시행세칙·유권해석을 수시로 바꾸고(1200%룰 GA 확대, 분급제, 비교공시 등), 사규(직급별 지급률, 시책)는 그보다 더 자주 바뀐다. 따라서 설계의 제1원칙은 다음과 같다.

1. **룰은 코드가 아니라 데이터다.** 요율·한도·환수율·지급률은 전부 유효기간(effective date)을 가진 버전 데이터로 관리하고, 계산 엔진은 "기준일에 유효한 버전"을 조회해서 쓴다.
2. **계산 구조가 바뀌는 변경(새 규제 도입 등)은 새로운 계산 Step을 추가하는 방식으로 대응한다.** 기존 Step은 절대 수정하지 않고 버전으로 대체한다.
3. **모든 계산 결과는 불변(immutable)이며, 정정은 취소분개(reversal) + 재계산(rebook)으로만 한다.** 이것이 정확성·감사가능성·재현가능성의 기반이다.
4. **돈 계산은 전부 BigDecimal + 중앙화된 반올림 정책.** double/float 금지.
5. **(v1.1 신설) 순액은 전 상태 합산으로만 구한다(합산 규약, §3.0).** REVERSED 원본도 합산에 남고 음수 reversal이 상쇄한다. 어떤 조회·공시·대사 쿼리도 상태 필터로 금액을 걸러서는 안 된다.

> 원칙 1~4는 Phase 0~9 구현에서 그대로 관철되었음이 확인됐다. 특히 "룰 조회는 기준일 필수" 규약 덕에 2026-06-30/07-01 한도 경계, 2027 분급 시행 같은 시행일 분기가 전부 코드 분기 없이 데이터 문제로 환원됐다.

## 2. 도메인 개요

### 2.1 수수료 흐름 (GA의 양면성)

GA는 수수료의 **수취자이자 지급자**다. 두 흐름을 반드시 분리해서 모델링한다.

```
[보험사(원수사) N개] --(EDI/수수료명세)--> [GA: 매출측 수수료(INBOUND)]
                                              |
                                              v  (지급률/시책/한도/분급/환수 적용)
                                         [GA: 비용측 수수료(OUTBOUND)]
                                              |
                                              v
                              [설계사 개인 + 조직(팀장/지점장/본부) 오버라이드]
```

- **매출측(INBOUND)**: 보험사가 GA에 지급하는 수수료. 보험사마다 상품·요율·명세 포맷이 전부 다르다. 자체 계산치와 보험사 명세를 **대사(reconciliation)** 해야 한다.
- **비용측(OUTBOUND)**: GA가 설계사에게 지급하는 수수료. 1200%룰(2026.7~)과 분급제(2027.1~)가 직접 적용되는 영역. 본 시스템의 핵심.
- 두 흐름의 차이가 GA의 마진이며, 계약·설계사·상품 단위 마진 분석이 가능해야 한다.

### 2.2 수수료 유형 (OUTBOUND 기준)

| 유형 | 코드 예시 | 설명 | 1200% 한도 포함 |
|---|---|---|---|
| 초년도 모집수수료 | `FY_COMM` | 신계약 체결에 따른 수수료. 회차(1~12회차)별 요율 존재 | 포함 |
| 계속(유지)수수료 | `RENEWAL` | 2차년도 이후 계속보험료 입금 시 | 미포함(초년도 아님) |
| 시책/프로모션 | `INCENTIVE` | 기간·상품·실적 조건부 인센티브 | **포함(2026.7~)** |
| 정착지원금 | `SETTLEMENT_SUPPORT` | 설계사 영입/정착 지원 | **포함(2026.7~)** |
| 오버라이드(조직수수료) | `OVERRIDE` | 팀장/지점장/본부장 등 상위 조직 지급분 | 적용 기준 확인 필요 → 플래그로 관리. "포함"으로 확정될 경우 `limit_included='Y'` 데이터 변경 + LimitGateStep V2(수급자 범위 확장) 등록으로 흡수 — 기존 Step 무수정 |
| 분급 수수료 | `DEFERRED` | 2027.1~ 분급 스케줄에 따른 이연 지급분 | 스케줄 자체가 한도의 산출물 (한도는 분할 전 총액으로 소진, §6.2) |
| 유지관리수수료 | `MAINTENANCE` | 2029 로드맵. 유지율 연동 | 미포함 예상, 고시 확인 |
| 환수 | `CLAWBACK` | 해약/실효/철회/미유지 시 회수 (음수 지급) | 한도 원장에서 차감 (원복은 DTL 부호 반전, §6.1.7) |

한도 포함 여부는 하드코딩하지 말고 `COMM_TYPE` 마스터의 속성(유효기간 포함)으로 둔다.

### 2.3 수수료 라이프사이클 이벤트

수수료는 스스로 발생하지 않고 **계약 이벤트에서 파생**된다. 이벤트 주도로 설계한다.

| 이벤트 | 수수료 영향 |
|---|---|
| 신계약 체결(청약 승인) | 초년도 수수료 발생, 1200% 한도 원장 개설, (2027~) 분급 스케줄 생성 |
| 회차 보험료 입금 | 회차별 수수료 발생, 분급 조건 충족 체크 |
| 청약철회 | 기지급 수수료 전액 환수 |
| 해약/실효 | 환수율 테이블에 따른 환수, 분급 스케줄 중단 |
| 부활 | 수수료/스케줄 재개 (환수분 재지급 여부는 사규 → `ReviveStep.RevivePolicy` 파라미터) |
| 감액/보험료 변경 | 월납보험료 변경 → **1200% 한도액 재산정**, 분급 스케줄 조정 |
| 설계사 이동/해촉 | 잔여 분급·환수 귀속 처리 (고아 수수료 정책) |
| 보험사 정정 명세 수신 | 매출측 정정 → 비용측 재계산 트리거 |

### 2.4 조직·설계사

- 설계사: 위촉코드, 직급/등급(지급률 결정), 위촉일/해촉일, 소속 이력(조직 이동 이력 필수 — 지급 시점 소속 기준인지 계약 시점 소속 기준인지는 사규 파라미터 `AffiliationBasis`).
- 조직: 트리 구조(본부-지점-팀), 오버라이드 배분율은 계층별 요율 테이블.
- 세무: 설계사는 통상 사업소득자 → 지급 시 3.3% 원천징수(소득세 3% + 지방소득세 0.3%), 지급명세서 산출. 원천세는 **상계 후 순지급액 기준**으로 지급 단계(`PayoutService`)에서 계산하며, 세율·절사 규칙은 `WithholdingTaxPolicy`로 교체 가능. 환수 상계분의 지급조서 반영 방식은 세무 확인 필요(§11.11).

## 3. 핵심 설계 원칙

### 3.0 합산 규약 (Netting Convention) — v1.1 신설, 위반 금지

**순액(수급자×유형×기간의 확정 금액)은 상태 필터 없이 전 레코드 합산으로만 구한다.**

- REVERSED 상태의 원본 레코드는 합산에서 **빠지지 않는다.** 원본을 상쇄하는 것은 음수 reversal 레코드다.
- 이 규약 하나로 다음이 통일된다: 마감월 불변성(과거 숫자 불변), 지급/환수 회계, PAID 상태 원본의 정정(동일 산식), 환수 기준액(순기지급) 계산.
- **금지 사항**: 금액을 합산하는 어떤 쿼리(REST 조회, 공시 산출, 대사, 리포트)에서도 `status != 'REVERSED'` 같은 상태 필터를 걸어서는 안 된다. 상태 필터는 워크플로 조회(건수·목록)에만 허용된다.
- **강제 수단**: 순액 산출은 조회 계층의 공용 합산 컴포넌트(예: `NetAmountCalculator`)를 통해서만 한다. 개별 서비스가 SUM 쿼리를 직접 작성하는 것을 코드리뷰 규약으로 금지하고, README 핵심 규약에 명문화한다.
- **실증 (v1.1.4)**: Phase 11에서 정산 순액 계산이 CALCULATED 상태 필터를 쓰고 있어, 마감 전 정정(원본 REVERSED·reversal·rebook이 같은 월에 공존) 시 원본은 빠지고 음수 reversal만 합산되어 **이중 차감(과소 지급)** 하는 잠복 결함이 발견됐다. 이 규약이 존재하는 이유이며, 이후 순액 산출 신규 코드는 예외 없이 공용 컴포넌트를 경유한다. 해당 조합(마감 전 정정 3종 공존)은 회귀 테스트로 고정됐다.

### 3.1 Effective-Dated + 버전 관리 (이중 시간축 권장)

- 모든 룰/요율 레코드는 `apply_from`, `apply_to`(업무 유효기간) + `created_at`, `superseded_at`(시스템 기록기간)을 가진다.
- 업무 시간축: "이 계약(2026.8.1 체결)에는 어떤 요율이 적용되나" → 기준일로 조회.
- 시스템 시간축: "지난달 마감 때는 어떤 요율로 계산했나" → 소급 정정·감사 대응. 완전한 bitemporal이 부담이면 최소한 "계산 결과에 사용한 룰 버전 ID를 박제"하는 방식으로 재현성을 확보한다(필수 — 구현 완료).

### 3.2 불변 원장 + 취소/재분개(Reversal & Rebook)

- `COMM_CALC` 레코드는 생성 후 UPDATE 금지(상태 전이 제외). 오류 정정은 원본을 참조하는 음수 reversal 레코드 + 신규 레코드.
- 마감(월마감) 확정된 기간의 레코드는 절대 불변. 마감 후 발견된 오류는 익월 조정(`ADJUSTMENT`)으로 반영.

### 3.3 결정론적 계산 + 근거 박제

- 동일 입력 + 동일 룰 버전 → 항상 동일 출력(멱등). 계산 결과에는 사용된 룰 버전 ID 목록, 입력 스냅샷, 단계별 중간값(trace)을 JSON으로 저장한다. → 감사·민원·당국 검사 대응.
- replay(재현)는 §6.5의 원장 재구성 절차를 따라야 결정론이 보장된다.

### 3.4 한도는 원장으로, 검증은 지급 전에

- 1200% 한도는 사후 리포트가 아니라 **지급 파이프라인의 게이트**다. 초과분은 자동 삭감/이연되고 사유가 기록된다.
- 게이트 판정과 원장 전기는 단계가 분리되지만(§4.2) **하나의 트랜잭션·하나의 락 범위** 안에 있어야 한다(§6.1.6).

### 3.5 도메인 로직의 프레임워크 독립

- 계산 엔진(core)은 Spring/Oracle 무의존 순수 Java 모듈로 만들어 단위 테스트를 밀리초 단위로 돌린다. DB·배치는 어댑터. 인메모리 Store 구현이 규약(불변 원장, 멱등키, 상태 전이)의 **레퍼런스 구현**이며, Oracle 어댑터는 계약 테스트(§8.7)로 동등성을 증명한다.

### 3.6 룰 관리 전략: 하이브리드 (범용 룰엔진 비권장)

Drools 같은 범용 룰엔진은 이 도메인에서 디버깅·감사·성능·학습비용 문제가 크다. 대신 3계층 하이브리드를 권장한다. (구현 검증: 4년→7년 분급 확장이 커브 레코드 추가만으로 동작함을 테스트로 증명)

| 계층 | 관리 방식 | 예시 | 변경 시 배포 필요 |
|---|---|---|---|
| 요율·파라미터 | DB 테이블 (유효기간+버전) | 회차별 요율, 지급률, 환수율, 한도 배수(12배), 분급 커브 | 아니오 |
| 조건식 | 제한된 표현식(SpEL, **샌드박스 필수**) 또는 설정 플래그 | 시책 조건(§5.10), "한도 포함 여부", "부활 시 재지급 여부" | 아니오 |
| 계산 구조 | 버전이 붙은 코드 Step (전략 패턴) | 1200% 한도 로직 자체, 분급 알고리즘 | 예 (신규 Step 추가) |

새 규제가 나오면: ① 파라미터로 흡수 가능한가 → 테이블 등록으로 끝. ② 새 계산 단계가 필요한가 → 새 `CalculationStep` 구현 + 유효기간 등록. 기존 코드는 건드리지 않는다.

### 4.2 계산 파이프라인 — v1.1 개정

계산 단위는 `(계약이벤트 × 수급자)`. 하나의 이벤트가 설계사 본인 + 조직 오버라이드 수급자 여러 명의 계산을 낳는다.

v1.0과의 차이: ① 원장 전기가 Step에서 **저장 후 훅**으로 이동(사유: DTL 근거 무결성 — 전기에는 확정된 calcId가 필요하다), ② `ClawbackOffsetStep`·`WithholdingTaxStep`을 파이프라인에서 제거하고 각각 지급 런 단위 서비스·지급 단계로 이동(사유: 상계·과세는 개별 계산이 아니라 순액 확정 시점의 일이며, 파이프라인 내 상계는 이중 상계 위험이 있다).

```
PolicyEvent 수신
  → [1] 검증/정규화 (보험사별 어댑터, 중복 이벤트 멱등 처리: 이벤트 natural key)
  → [2] 수급자 결정 (설계사 + 오버라이드 체인, 기준: AffiliationBasis 파라미터)
  → [3] 룰 해석 (기준일로 요율/지급률/한도룰/분급룰/환수룰 버전 확정 → RuleSnapshot)
  → [3.5] ★ 한도 원장 락 획득 (한도 대상 계산인 경우, §6.1.6 — 게이트 판정 이전에 획득)
  → [4] 계산 Step 체인 실행:
        BaseCommissionStep  (order 10)  기본 수수료 = 산출기준액 × 요율
        PayoutRateStep      (order 20)  직급/등급 지급률 적용
        IncentiveStep       (order 30)  시책 계산 (조건 충족 검증)
        LimitGateStep       (order 50)  ★ 1200% 한도 판정 (삭감/이연 결정만, 전기는 하지 않음)
        DeferralSplitStep   (order 55)  ★ 분급 스케줄 분할 (2027-01-01부터 활성)
  → [5] 결과 저장 (COMM_CALC + trace + 사용 룰버전) — 상태 CALCULATED, calcId 확정
  → [5.5] ★ 저장 후 훅 (CalcResultListener 체인, 동일 트랜잭션):
        LimitLedgerPoster    확정된 calcId로 LIMIT_LEDGER_DTL 전기 + 원장 가산
        (분급 스케줄 확정 등 calcId 의존 후처리도 이 단계)
  → [커밋] — 락 해제는 커밋 시점
  → [6] 월마감 배치에서 확정(CONFIRMED) → 지급 런에서 상계·원천세 → 지급(PAID)
```

각 Step은 아래 인터페이스를 구현하며, **Step 목록 자체도 유효기간을 가진 설정**이다(예: `DeferralSplitStep`은 2027-01-01부터 활성).

> **배치 트랜잭션 경계 (v1.1.5)**: [3.5]~[5.5]는 **항목(이벤트×수급자) 하나의 업무 트랜잭션**으로 닫힌다. 계산·지급을 포함하는 배치 잡은 스텝 트랜잭션 매니저를 무자원(Resourceless)으로 두고 태스크릿 반복 1회마다 업무 트랜잭션 1개를 열어, 청크가 한도 락을 여러 항목에 걸쳐 보유하는 구조를 원천 차단한다(§6.1.6, §10 Phase 11).

### 4.3 핵심 인터페이스 (Java 스케치) — v1.1 개정

```java
/** 금액: BigDecimal 래핑, 통화/스케일/반올림 정책 강제. 생성 후 불변 */
public final class Money implements Comparable<Money> {
    private final BigDecimal amount;          // scale 고정
    public Money multiply(Rate rate, RoundingPolicy policy) { ... }
    // plus/minus/negate/isNegative ... 산술은 전부 여기서만
}

/** 반올림 정책: 코드 전체에서 이 클래스 외 RoundingMode 직접 사용 금지 */
public enum RoundingPolicy {
```

### 5.10 시책 마스터 (INCENTIVE_MST, Phase 13) — v1.1.7 본문 승격

요율 마스터(§5.2)와 동일한 유효기간+버전+승인 패턴을 따른다. 요율과 다른 점은 ① 대상 필터가
NULL=전체(와일드카드)이고, ② **조건식이 실행 가능한 표현식(SpEL)** 이라는 것 — 그래서 이 테이블은
이 시스템에서 유일하게 "사용자 입력이 실행되는" 표면이며, 조건식은 반드시 샌드박스에서만 평가된다
(§3.6, 부록 B-16).

```sql
CREATE TABLE INCENTIVE_MST (
  incentive_id   NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  incentive_cd   VARCHAR2(30) NOT NULL,     -- 시책 식별 코드 = 버전/겹침 불변식의 키
  insurer_cd     VARCHAR2(10),              -- NULL = 전체 보험사 (와일드카드)
  product_key    VARCHAR2(40),              -- NULL = 전체 상품
  channel        VARCHAR2(20),              -- NULL = 전체 채널
  condition_expr VARCHAR2(1000) NOT NULL,   -- ★ SpEL 조건식. 등록·승인·평가 시 샌드박스 검증
  payout_kind    VARCHAR2(16) NOT NULL,     -- FIXED / PREMIUM_RATE (산식 확장은 새 종류로, B-12)
  fixed_amount   NUMBER(15),                -- FIXED 전용
  premium_rate   NUMBER(9,6),               -- PREMIUM_RATE 전용
  apply_from     DATE NOT NULL,
  apply_to       DATE DEFAULT DATE '9999-12-31' NOT NULL,
  version_no     NUMBER NOT NULL,
  status         VARCHAR2(10) NOT NULL,     -- DRAFT/ACTIVE/SUPERSEDED
  created_by/at, approved_by/at,
  CONSTRAINT ck_incentive_status CHECK (status IN ('DRAFT','ACTIVE','SUPERSEDED')),
  CONSTRAINT ck_incentive_kind   CHECK (payout_kind IN ('FIXED','PREMIUM_RATE'))
);
-- INCENTIVE_CHANGE_HIST: COMM_RATE_CHANGE_HIST와 동형 (change_type TRIM/SUPERSEDE/ACTIVATE/DISCARD,
--   diff 자동 도출로 기록 누락 불가). INCENTIVE_ADMIN_SEQ START 1000000 (identity와 분리된 대역).
```

- **겹침 불변식은 같은 `incentive_cd`에 대해서만** 성립한다 — 서로 다른 시책은 중첩 적용되므로 요율처럼
  "키당 단건 해석"이 아니라 기준일 유효 ACTIVE **전부**를 조회해 각 조건을 판정한다.
- **재현성**: 계산에 실제 사용된 시책 버전을 `COMM_CALC.rule_versions`에 박제하고, 조건 판정 결과(어떤
  시책·참/거짓·금액)를 `calc_trace`에 기록한다(§6.5 replay).
- **동시성 최종 심판**: ACTIVE 대상 function-based unique index `ux_incentive_active`(V102, Phase 14
  선행) — 요율 `ux_comm_rate_active`와 동형이되 대상 필터가 nullable이라 `NVL('*')`로 감싼다(전체-대상
  ACTIVE 중복이 NULL 비교로 새는 것을 막는다). 인덱스 위반은 어댑터가 `IncentiveApprovalConflictException`
  (→409)으로 번역해 명시적 거부한다. 단 인덱스는 (키+개시일) 충돌만 심판하므로 개시일이 다른 겹침
  경합은 새며, **과지급을 막는 것은 인덱스가 아니라 룰 해석 Ambiguous fail-fast**(v1.1.9 선행 —
  기준일에 같은 `incentive_cd` 적용 ACTIVE가 2건 이상이면 계산 거부, `IncentiveV2Step`). 승인 경합
  **재시도 러너 + 결정적 인터리빙 IT**는 요율(§6.6)과 동형으로 후속 과제이며 순수 편의 개선이다
  (명세: 락 획득 후 재검증).

부가 테이블(구현 시 추가): 계약 마스터/보험료 변경 이력, 설계사 마스터/소속·등급 이력, 조직 트리 이력, INBOUND 명세 원장, 대사 결과, 지급 배치/이체 파일(정산행 `AGENT_SETTLEMENT`는 지급 런 회차 `run_seq`를 가진다 — 같은 마감월 월 N회 지급 런 구분, §7), 원천세. **(v1.1.3)** `AGENT_ORG_HIST`의 PK는 (agent_id, apply_from)이 아니라 **(agent_id, org_id, apply_from)** — 한 설계사가 같은 시점에 팀+지점+본부 3계층 소속 행을 동시에 가지므로 agent_id+apply_from만으로는 체인을 담지 못한다(V8 반영 완료). 승인 워크플로의 신규 행 채번은 identity가 아닌 **전용 시퀀스(별도 대역)** 를 사용해 시드/수기 등록 대역과의 충돌을 차단한다.

## 6. 핵심 엔진 상세

### 6.1 1200% 한도 엔진 — v1.1 개정 (판정과 전기의 분리 + 단일 락 범위)

1. **대상 판정**: 계약 체결일로 `LimitRule` 버전 조회. GA→설계사 적용은 2026-07-01 이후 체결 계약(그 이전 계약은 미적용) — 이 분기 자체가 룰 데이터다.
2. **원장 조회/생성**: `(policy_no, agent_id)` 로 `LIMIT_LEDGER` 확보. `limit_amount = monthly_premium × limit_multiple`.
3. **합산 대상 판정**: 이번 계산 라인 중 `COMM_TYPE_MST.limit_included='Y'`(기준일 유효 버전) 항목만 합산.
4. **게이트 (LimitGateStep, order 50)**: `available = limit_amount − accum_paid`.
   - `calc_amount ≤ available` → 통과.
   - 초과 → `LIMIT_RULE.over_limit_action` 파라미터에 따라 ① 초과분 삭감(CUT) 또는 ② 초년도 종료 후 이연(DEFER_AFTER_FY). 어느 쪽이든 `limit_cut_amt`와 사유를 기록.
   - **(v1.1.1) 코드에는 초과 처리 기본값을 두지 않는다(의도적).** 처리 방식은 전적으로 룰 데이터를 따르며, `over_limit_action`이 누락된 한도 대상 계산은 **fail-fast(계산 거부 + 명시적 오류)** 한다. 침묵 기본값은 잘못된 정책으로 지급이 나가는 컴플라이언스 사고로 직결되므로 금지. 운영 시드 데이터에는 규정 위반 방지 관점에서 **DEFER_AFTER_FY(차단+이연) 등록을 권고**하며, 시드 확인은 배포 체크리스트 항목이다(§11.3).
   - **게이트는 판정만 한다. 원장 전기는 하지 않는다.**
5. **전기 (LimitLedgerPoster, 저장 후 훅)**: `COMM_CALC` 저장으로 calcId가 확정된 직후, 동일 트랜잭션의 `CalcResultListener` 체인에서 `LIMIT_LEDGER_DTL`에 전기(posting_seq 채번)하고 원장 `accum_paid`를 가산한다. 전기에 확정 calcId가 필요하다는 근거 무결성 요구 때문에 저장 전 전기는 불가능하며, 이것이 훅 단계가 존재하는 이유다.
6. **락 규약 (필수 — 게이트와 전기는 하나의 직렬화 단위)**:
   - 한도 대상 계산 트랜잭션은 **게이트 판정 이전**(§4.2 [3.5])에 해당 원장 행을 `SELECT ... FOR UPDATE`로 획득하고, 그 락은 **훅의 전기와 커밋까지 유지**한다. 판정 시점과 전기 시점 사이에 다른 트랜잭션이 같은 원장을 읽으면 둘 다 잔여 한도를 통과한 뒤 각자 전기해 한도를 초과하는 경합 창이 생기기 때문이다.
   - 원장 행이 아직 없는 신계약 동시 유입은 `uq_limit` 유니크 제약 위반 시 재시도로 직렬화한다.
   - **배치에서의 락 보유 구간 (v1.1.5)**: 계산·지급 배치 잡은 청크가 락을 여러 항목에 걸쳐 보유하지 않도록 **항목 단위 업무 트랜잭션**으로 실행한다(§4.2, §10 Phase 11). 청크 크기와 무관하게 [3.5]~[5.5]가 항목 안에서 닫힌다.
   - **인메모리 구현은 이 경합을 재현하지 못한다.** Oracle 어댑터에서 동일 원장 대상 동시 계산 2건을 실제 경합시키는 동시성 테스트(§8.6)를 필수로 둔다. 속성 테스트(시드 고정 생성기, v1.2.2 이전 jqwik) 불변식 통과는 단일 스레드 기준임을 잊지 말 것.
7. **취소분개 시 원복 (LimitReversalHook)**: 유형별 재판정이 아니라 **원본 calcId로 전기된 DTL 금액 합의 부호 반전 전기**로 처리한다. 정확하며, 이후 한도 포함 유형 정의가 바뀌어도 과거 원복에 영향이 없다.
8. **재산정 트리거**: 보험료 감액/증액 이벤트 → `monthly_premium` 갱신 및 한도 재계산. 기지급 누적이 신한도를 초과하는 경우 기본 동작은 **향후 지급 중단**(available=0으로 자연 차단)이며, "환수 전환"으로 유권해석이 확정되면 신규 Step으로 흡수한다(§11.4).

불변식(테스트로 상시 검증): **어떤 시점에도 `accum_paid ≤ limit_amount`**, `accum_paid = Σ LIMIT_LEDGER_DTL.amount`.

### 6.2 분급 엔진 (2027.1 대비 — 구조 구현 완료)

- 분급 커브를 데이터로: `DEFERRAL_CURVE(curve_id, apply_from, apply_to)` + `DEFERRAL_CURVE_DTL(curve_id, year_no or month_no, pct)`. 2027 커브(4년), 2029 커브(7년)를 레코드로만 추가. (완성 기준 충족: 7년 커브는 데이터 교체만으로 동작함을 테스트로 증명)
- 신계약 계산 시 `DeferralSplitStep`(order 55)이 초년도 지급분/이연분을 분할하고 `DEFERRAL_SCHEDULE` 생성.
- **분급×한도 상호작용 (v1.1 확정)**: 한도는 **분할 전 총액**으로 소진된다("스케줄 자체가 한도의 산출물", §2.2). 따라서 Step 순서는 LimitGate(50) → DeferralSplit(55)로 고정하며, DEFERRED 도래 지급은 게이트를 재통과하지 않는다.
- **분급 반올림 (v1.1 확정)**: 각 포인트 절사 배분 + 마지막 포인트가 잔여를 흡수 → "스케줄 합 = 이연 원금" 불변식이 임의 금액에서 성립(property 테스트로 증명).
- 월 배치가 도래분(`due_ym = 당월`) 중 `pay_condition` 충족 건을 RELEASED로 전환해 지급 파이프라인에 투입. 해약/실효 이벤트는 잔여 스케줄 CANCELLED.
- 세부 요율(유지관리수수료 월 0.8% 등)은 고시 확정 전이므로 **커브 데이터 등록만으로 대응 가능해야 한다**는 것이 이 모듈의 완성 기준(충족).

### 6.3 환수 엔진 — v1.1 개정 (상계의 위치 이동)

- 트리거: CANCEL/LAPSE/WITHDRAW/REDUCE 이벤트.
- 환수액 = 기지급 수수료(환수 대상 유형만) × 경과 회차 구간별 환수율(`CLAWBACK_RULE`, 계약일 기준 버전). **환수 기준액(기지급)은 합산 규약(§3.0)에 따른 순기지급**이다.
- 환수는 음수 `COMM_CALC` 로 생성된다. **상계는 파이프라인 Step이 아니라 `ClawbackOffsetService`가 수행한다** — 상계는 개별 계산 시점이 아니라 월 순액이 확정되는 시점의 일이며, 파이프라인 내 상계는 이중 상계 위험이 있기 때문이다(v1.0의 ClawbackOffsetStep 폐기).
- `ClawbackOffsetService`는 **지급 런 단위**로 호출된다. 지급 주기가 월 2회 등으로 확정되면(§11.12) 호출 지점이 지급 런마다 반복되므로 **마감 절차에 하드결합하지 않는다.**
- 상계 후 부족분은 `CLAWBACK_RECEIVABLE` 채권화 → 이후 지급 런에서 자동 상계. 해촉자 채권은 별도 회수 프로세스(범위 외, 데이터만 제공).
- 환수 발생 시 `LIMIT_LEDGER.accum_paid` 차감(초년도 윈도우 내인 경우) — 한도 여유가 다시 생기는지 여부도 유권해석 확인 대상 → 파라미터.

### 6.4 정정·재계산 (Reversal & Rebook) — v1.1 개정

- 입력 오류/보험사 정정 명세/룰 소급 변경 시: 대상 `COMM_CALC` 상태를 REVERSED로 전이 + 음수 reversal 레코드 생성(원본 참조) + 새 룰로 재계산 레코드 생성. **합산 규약(§3.0)에 따라 REVERSED 원본은 합산에 남고 reversal이 상쇄한다** — PAID 상태 원본의 정정도 동일 산식이다.
- 미마감월 건은 당월 내 정정, 마감월 건은 `ADJUSTMENT`로 익월 귀속. **과거 마감 숫자는 절대 바뀌지 않는다.**
- **멱등의 2층위 (v1.1 확정)**:
  - 레코드 수준(같은 원본에 reversal 중복 생성 방지)은 REVERSED 상태 체크로 **엔진이 보장**한다.
  - 값 수준(같은 재계산을 두 번 돌려도 수급자×유형 순액 동일)은 **테스트로 증명**한다.
  - 배치 요청 단위 dedup(같은 재계산 요청의 중복 실행 차단)은 **배치 계층의 책임**(요청 ID)이다. 구현: Spring Batch `JobInstance`(잡 이름 × 식별 파라미터)를 요청 저장소로 사용 — 완료 인스턴스 재제출은 no-op, 실패 인스턴스 재제출은 재시작(§10 Phase 11).

### 6.5 감사 재현 (Replay) — v1.1 신설 (절차 명문화)

임의 `calc_id`에 대해 당시와 동일한 금액을 재산출하는 절차:

1. `COMM_CALC.rule_versions`로 당시 룰 버전을, `calc_trace`·입력 스냅샷으로 입력을 복원한다.
2. **한도 원장 상태 재구성**: 한도 게이트 라인의 재현에는 "계산 시점의 원장 상태"가 필요하다. `LIMIT_LEDGER_DTL`에서 **대상 calc의 전기 이전까지의 합**으로 원장을 재구성해 파이프라인에 물린다.
3. **'이전'의 정렬 기준은 `posting_seq`(단조 증가 전기 순번)다. `posted_at` 타임스탬프를 정렬 기준으로 쓰지 않는다** — 동시각 충돌·클럭 문제로 재현이 비결정적이 되기 때문이다. 이것이 §5.6에 posting_seq를 둔 이유다.
4. 재산출 금액이 원본과 일치하면 재현 성공. 불일치 시 소급 룰 변경 검출로 리포트한다.

이 절차는 감사 대응 절차서(운영 문서)에도 동일하게 명문화한다.

### 6.6 룰 버전 교체 시맨틱 — v1.1 확정

- 승인 시 기존 ACTIVE 버전은 **트리밍**(신규 버전 개시일 전날로 종료) 또는 **SUPERSEDE**(완전 덮임) 중 하나로만 처리한다.
- **기존 버전의 유효기간을 분할하는 승인은 명시적으로 거부한다.** "같은 키에 겹치는 ACTIVE 없음" 불변식을 단순하게 지키기 위함이다.
- 이 불변식의 강제는 3중이다: ① 승인 워크플로(앱 계층, 이식성 확보), ② Oracle function-based unique index(ACTIVE 행 대상, DDL 이중화), ③ 마감 배치의 Ambiguous(중복 유효 룰) 검출 리포트(안전망).
- **(v1.1.2) 승인 동시성 규약**: 같은 키에 대한 동시 승인 2건은 앱 계층 겹침 검사를 둘 다 통과할 수 있다. 최종 심판은 **function-based unique index**이며, 승인 트랜잭션은 인덱스 위반을 예외가 아닌 정상 경합으로 취급해 **재시도(최신 상태 재조회 후 재검증) 또는 명시적 거부**로 처리한다 — `uq_limit` 재시도 패턴과 동일. Oracle 어댑터(Phase 10b)의 계약 테스트에 이 경합 케이스를 필수 포함한다.
- **(v1.1.2) 트리밍의 변경 감사**: 트리밍은 기존 ACTIVE 행의 `apply_to`를 UPDATE하는 예외적 변경이므로, 변경 전후 값·승인자·시각을 담은 **룰 변경 이력**을 반드시 남긴다(별도 이력 테이블 또는 감사 로그). 계산 재현성 자체는 `COMM_CALC.rule_versions` 박제로 이미 보장되지만, "지난달 룰 테이블이 어떤 모습이었나"(시스템 시간축, §3.1)에 답하려면 변경 이력이 필요하다.
- **(v1.1.3) 감사 기록의 도출 방식 표준**: 변경 이력은 서비스 계층의 선의가 아니라 **저장소 교체(replace)의 전후 diff에서 자동 도출**한다(TRIM/SUPERSEDE/ACTIVATE/DISCARD) — 기록 누락이 구조적으로 불가능해야 한다. 경합 시 패자의 중복 트리밍은 no-op diff로 이력이 중복되지 않는다. 이 패턴은 향후 다른 마스터(분급 커브, 환수율 등)의 관리 기능에도 동일 적용한다.
- **(v1.1.3) 승인자 실명 요건**: 감사 이력의 승인자가 "system"으로 남는 경로는 시드/테스트에서만 허용한다. 운영 승인 경로는 실제 승인자 식별자를 필수로 전달한다.
- **(v1.1.3) 승인 경합의 정합 기준과 거버넌스**: 경합 해소의 정합 기준은 **직렬 실행 동치**다 — 동시 승인 A·B의 종국 상태는 순차 실행(A→B 또는 B→A)의 결과와 같아야 하며, 그 이외의 상태(겹치는 ACTIVE, 유실된 승인)는 결함이다. 다만 근접 동시 승인은 프로세스 이상 신호일 수 있으므로, 변경 이력에서 **짧은 시간 내 동일 키 경합(ACTIVATE 직후 SUPERSEDE)을 감지해 관리자에게 알리는 리포트**를 운영 기능으로 둔다(마감 리포트 또는 관리 화면).

### 6.7 비교설명 판매수수료 등급·순위 API — v1.2.2 신설 (Phase E3)

**계약.** 정본은 `ga-disclosure` 저장소 `contracts/api/v1/engine-disclosure.openapi.yaml`(1.1.0)이고 이 저장소 `contracts/api/v1/`에 복사해 `contracts/CHECKSUMS`(sha256sum 형식)·`contracts/UPSTREAM`(출처 커밋)으로 일치를 검사한다(`verifyContractChecksums`는 `check`, `verifyUpstreamContract`는 CI). 이 저장소에서 계약을 고치지 않는다 — 바꿀 일이 있으면 ga-disclosure에서 먼저.

```json
                          "INSUFFICIENT_POPULATION": "INSUFFICIENT_POPULATION", "TEMP_PRODUCT": "TEMP_PRODUCT" } }
```

- 경계는 **문자열 10진수 + 포함 여부 플래그**를 함께 적는다(숫자 JSON 거부, 포함 여부 기본값 없음). 로드 시: 하한 없는 구간·상한 없는 구간이 정확히 1개씩, 인접 경계는 값이 같고 포함 여부가 상보적(둘 다 제외 = 빈틈, 둘 다 포함 = 겹침), ordinal은 비율 순으로 엄격 증가, 코드·ordinal 유일, 라벨 필수. 위반은 `INVALID_POLICY`(스냅샷 미발급).
- `unavailableReasons`는 **원인(엔진이 판정하는 상황, 닫힌 어휘) → 사유 코드(데이터)** 맵이다. 사유 코드 문자열을 코드 상수로 두지 않기 위해 지시문 예시의 목록 형태를 맵으로 바꿨다.
- 순위 정책 body: `{ "tieBreak": "SHARED_RANK" }` 또는 `{ "tieBreak": "STRICT", "secondaryKeys": ["MEASURE_ASC", "PRODUCT_KEY_ASC"] }`(STRICT는 `PRODUCT_KEY_ASC` 필수 — 전순서 보장).
- 두 정책 모두 `apply_from`/`apply_to`(양끝 포함, 기본 9999-12-31)·`status`(DRAFT/ACTIVE/SUPERSEDED)를 가진 버전 레코드이고 요청 `asOfDate`로 단건 해석한다(2건 → 409, 0건 → 422). 같은 `apply_from`의 ACTIVE 중복은 함수 기반 유니크 인덱스가 2차로 막는다(V103, §6.6과 같은 구조).

**측정(모수) — 예시 측정.** `measureKey → 측정 함수` 레지스트리(앱 배선의 명시 목록). v1 `FY_SALES_COMMISSION_RATE`: 상품군 소속(`DISC_PRODUCT_GROUP_MEMBER` — 외부 `productKey` → `(insurer_cd, product_key)` 매핑)의 매출측 요율 `COMM_RATE(direction=INBOUND, comm_type=measureParams.commType, installment_no=measureParams.installmentNo)`을 **측정 기준일 = 요청 기준일이 속한 분기의 직전 분기 말일**(`basis.period` = 그 분기, 예: 2026-09-23 → 2026Q2)로 읽는다. 기준일 유효 요율 2건 이상은 Ambiguous. 요율이 있으나 그날 유효하지 않으면 `OUTSIDE_PERIOD`, 아예 없으면 `NO_RATE_DATA`, 소속이 아니면 `NOT_IN_GROUP`. 판매수수료율의 정확한 정의(모수·기간)는 **외부 확정 사실(§11 #13)이므로 이 함수는 예시이며 교체 대상**이다. `TEMP_PRODUCT`는 v1 측정이 판별 수단이 없어 만들지 않는다(데이터 목록 호환).

**평균 대비 비율(부록 B-1 개정).** 모집단 = 측정 기준일에 측정값이 있는 소속 상품(n = `groupPopulation`). n < `minPopulation`이거나 Σ=0이면 요청 전체가 `INSUFFICIENT_POPULATION`. 비율 = 측정값 × n / Σ 를 `RatioToAvg`에서 **한 번의 나눗셈·한 번의 반올림**(자릿수·모드는 정책)으로 만들고 `toPlainString()` 문자열을 이때 한 번 만든다(평균을 따로 반올림하지 않아 이중 반올림이 없다). 이후 어떤 경로도 이 문자열을 숫자로 되돌려 재포맷하지 않는다. **등급은 반올림된 비율로 판정**한다 — 인쇄되는 비율과 등급이 어긋나지 않게(예: "1.30"이 매우높음이 되는 일 없음). `TODO(confirm#13)`: 등급 판정을 원 비율로 할지는 외부 확정 사항.

**세트 내 순위.** 요청 세트의 OK 항목만, **원 측정값 오름차순**(수수료가 낮을수록 1순위, 규정 정의). SHARED_RANK = 경쟁 순위(1-2-2-4)·동값 전부 tie, STRICT = 2차 키로 1..m 순열·분리된 항목도 tie=true. 측정값↑ ⇒ 비율↑ ⇒ 반올림 비율 비감소 ⇒ 등급 비감소이므로 단조성은 구성상 성립하고, 응답 생성 후 **자기 검증**(순위 오름차순 ⇒ ordinal 비감소, 동순위 ⇒ 같은 ordinal, 순위 구조)이 다시 확인한다 — 실패는 정책 데이터 모순 신호이므로 500이 아니라 스냅샷을 만들지 않고 422. 응답 순서: OK를 순위(동순위는 productKey)순, 그 뒤 UNAVAILABLE을 요청 순.

**스냅샷 — 불변·재조회 바이트 동일.** 발급 트랜잭션 안에서 일자별 채번(`DISC_GRADE_SNAPSHOT_SEQ` 행 잠금, `GRD-{yyyyMMdd}-{6자리}`, 날짜는 Asia/Seoul 주입 시계) → 응답을 **RFC 8785 JCS**로 정규화 → SHA-256 → `DISC_GRADE_SNAPSHOT(response_canonical, response_sha256, …)` + `DISC_GRADE_SNAPSHOT_ITEM`(ratio_to_avg는 VARCHAR2 원문, OK/UNAVAILABLE 필드 모양은 CHECK) 저장. POST 응답 본문이 이 정규 바이트이고, GET은 저장 원문의 해시를 대조한 뒤 **그대로** 돌려준다(재직렬화 없음, 불일치 시 500 `SNAPSHOT_INTEGRITY`). 정책·요율이 바뀌어도 옛 스냅샷은 재계산하지 않는다. `DISC_GRADE_SNAPSHOT(_ITEM)`의 UPDATE·DELETE는 **DB 트리거가 거부**한다(V103, ORA-20301/20302 — 엔진에서 처음으로 DB가 강제하는 불변; COMM_CALC의 UPDATE 금지는 규약 B-2).

**보안·격리.** `/internal/**`는 사람 계정(Basic) 체인과 분리된 무상태 체인이며 `Authorization: Bearer <서비스 토큰>`만 받는다 — 설정에는 토큰의 SHA-256(`app.internal.service-token-sha256`)만 두고 상수 시간 비교(운영은 mTLS 병행). 엔진은 테넌트별 인스턴스이므로 `app.tenant-id`와 요청 `tenantId`가 다르면 403이고, 이 검사가 격리의 전부다. 재조회는 저장된 `tenant_id`가 인스턴스 테넌트가 아니면 404. 두 설정 모두 기본값이 없고 비면 기동 실패(B-13).

```

D+1~     지급 런 (PayoutService — 지급 주기 파라미터에 따라 월 1회 이상 반복 가능):

```

## 8. 정확성 보장·테스트 전략 — v1.1 개정

1. **골든 테스트셋 (Phase 14 구현 완료)**: 정산 담당자가 엑셀로 검증한 대표 케이스(상품×이벤트×경계값)를 리포지토리에 **자기완결 CSV 번들**로 둔다 — 케이스 하나가 폴더 하나이며 [룰 시드 + 사건 타임라인 + 기대 결과]를 전부 담아 공유 시드에 기대지 않는다(규정 변경 = 기존 케이스 수정이 아니라 신규 케이스 추가, effective-dating 철학과 동일). CSV 디렉터리를 스캔하는 파라미터라이즈드 러너가 **전체 파이프라인을 경유해**(Step 우회 금지) 결과를 대조하고 불일치는 정산 담당자가 읽는 diff로 낸다. **CSV를 추가하는 것만으로 신규 케이스가 CI에 편입(코드 변경 0)**되고, 골든셋 실패는 빌드 실패다. 위치: `commission-settlement/src/test/resources/golden/`(작성 규약은 `golden/README.md`). JUnit에 남아 있던 골든 값 케이스는 이관 후 제거하고(중복 금지), 거동·property·계약·동시성 테스트만 코드로 존치한다.
2. **불변식 테스트(property-based — v1.2.2부터 JUnit 5 파라미터화 + 시드 고정 생성기 `SeededCases`, jqwik 제거·`net.jqwik` 차단)**: 한도 초과 절대 불가, reversal 합계 = 원본 합계 × −1, 분급 스케줄 합 = 이연 원금, 재계산 값 멱등성. (구현 완료 — 단, 단일 스레드 기준임에 유의)

## 12. 운영 전환 체크리스트 (v1.2.0 신설 — 시스템 밖 잔여)

Phase 16으로 **실행 가능한 앱 조립은 끝났다**(부트 앱·구성 외부화·인증·배치 기동·기동 스모크 E2E). 코드가 아닌 **운영·데이터·조직 절차**로 남는 항목을 여기 명시한다 — 이것들이 닫혀야 실제 정산에 투입할 수 있다.

1. **§11 미결정 회수 → 운영 시드 확정**: 전부 파라미터(룰 데이터)로 흡수돼 있으나 **배포 전 운영 시드 값**을 정산·컴플라이언스·세무 담당자와 확정해야 한다. 특히 `over_limit_action`(#3, 코드 기본값 없음 — 미설정 시 fail-fast), 초년도 윈도우(#1), 환수율 실값(#5), 분급 커브 확정(#8), 반올림 정책(#7). 확정 전엔 권고값(예: DEFER_AFTER_FY)으로 시드하되 fail-fast가 누락을 막는다.
2. **보험사별 INBOUND 어댑터 증설**: 현재 파일럿 1개(SAMLIFE CSV). 우선 연동 보험사(#9) 확정 후 어댑터를 데이터/코드로 증설한다(포맷별 `InsurerStatementAdapter` 추가, 이상 행은 조용히 스킵 금지).
3. **섀도 런 실데이터 병행(§8.5)**: 기존 시스템/수기 정산 결과로 **1~2개 마감 주기 병행 계산** 후 수급자×유형×마감월 전수 대조. 차이 유형(요율차/누락/타이밍/반올림)이 0으로 수렴하면 전환. `commission-shadow`가 프레임을 제공하며, 남은 건 실데이터 수입·판정이다.
4. **볼륨/성능 + 파티션 SPLIT 캘린더**: 실 볼륨으로 마감/지급/재계산 배치의 처리시간·락 경합을 측정한다. `COMM_CALC`는 RANGE+MAXVALUE 파티션(§5.5)이므로 **연 단위 SPLIT PARTITION을 DBA 절차·캘린더로** 운영한다(MAXVALUE 적재는 마감 리포트가 안전망으로 검출). HikariCP 풀·락 대기 타임아웃도 실측으로 재조정.
5. **감사 replay 운영 절차서(§6.5)**: 임의 `calc_id`의 원장 재구성·동일 금액 재산출은 코드로 검증돼 있으나, **감사 요청 대응 절차(권한·요청·산출물·보존)**를 운영 문서로 정립한다.
6. **PolicyStatusProvider 실 in-force 판정**: 분급 도래 시 유지 여부 판정이 현재 placeholder(항상 유지)다. 계약 상태 원장(실효/해약/부활)을 조회하는 실 판정으로 교체해야 분급 HELD/소멸이 운영에서 정확해진다. **운영 배포는 이미 구조로 막혀 있다**(v1.2.1) — prod에서 placeholder면 `PolicyStatusProviderGuard`가 기동을 실패시키므로, 실 판정 구현을 배선해야 비로소 prod가 뜬다(문서 표시가 아니라 구조적 차단, B-13). 이 항목은 "차단 해제 = 실 구현 배선"이 완료 조건이다.
7. **SSO 연동 + 인증 강제**: 현재 최소 인증(HTTP Basic + 외부 구성 인메모리 사용자)이며 **인증 없는 배포는 금지**다(사용자 미구성 시 아무도 통과 못 함). 사내 SSO(OIDC/SAML) `UserDetailsService`로 교체하고, 승인·마감·지급 역할을 조직 권한 체계에 매핑한다. principal 기반 실승인자는 이미 완결(§6.6).
8. **Flyway migrate 운영 절차**: 앱은 기동 시 `validate`만 한다(prod). 스키마 변경은 배포 파이프라인의 통제된 `flywayMigrate` 태스크로만 수행한다(운영 중 앱이 임의로 스키마를 바꾸지 않음).

16. **(v1.1.7) 관리자 입력 표현식은 샌드박스에서만.** 시책 조건식 등 관리자가 등록하는 표현식(SpEL)은 `SimpleEvaluationContext`(데이터 바인딩 전용)에서만 평가한다 — `T()` 타입 참조·빈 참조·생성자·메서드 호출·대입을 전부 거부하고, 프로퍼티 접근 + 연산자만 허용한다. 입력은 결정적 스냅샷(이벤트/설계사/사전 집계 실적)만 노출하고 시각·난수·외부 조회를 닿게 하지 않는다. 등록·승인 시 파싱+시평가로, 계산 시 평가 오류로 **fail-fast**(침묵 스킵 금지). 금지 구문 거부를 테스트로 고정한다 — 조건식 등록 화면이 곧 코드 실행 통로가 되지 않도록.
