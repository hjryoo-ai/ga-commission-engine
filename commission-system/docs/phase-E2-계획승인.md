# E2 계획 승인 (2026-10-17) — ga-commission-engine

## 판정: 승인. Q1~Q9 전부 권장안. P1~P17 권장안 전부 수용. 포털 계약 요청 R1~R8은 **A-1 채택과 한 PR(포털 계약 v1.3)** 로 — ⓪a 파일이 포털에 도착하는 즉시 포털이 만든다

읽은 것: `work/e2` = `4791307`의 `docs/phase-E2-계획.md` 전문. 포털 Phase 2 계획(`work/phase-2` = `d1d2a0a`)과 맞물리는 곳은 §3에. 지시문 형식을 바꾼 첫 Phase — 17건의 반증이 **계획 단계에서** 나왔고 지시문에는 결정만 남았다. 이 형식을 유지한다.

## 1. 인정하는 것

- **P3 — 기존 `dryRun`이 쓰고 잠근다는 발견**, 그리고 운영 저장소로 돌리면 E1 데코레이터가 `LimitLedgerOpened`를 적재한다는 것까지. "저장 없이"가 "리스너를 안 부른다"는 뜻일 뿐이었다는 문장이 이 계획의 핵심이다. 오버레이 저장소가 **구조적으로** 발행 경로에 닿지 않는다는 설계(Q1)가 거기서 나왔다.
- **P1·P2 — "예상 = 실제"가 깨지는 두 지점**(마감이 도래 분급을 넣는다, 상계는 쓴다)을 찾고, 미리보기를 **같은 반복 함수**(`previewConsume`/`consume`, `PayoutMath`)로 뽑아 두 경로가 갈라질 수 없게 한 것. S8·S9·S13이 그 세 함수 각각을 겨눈다.
- **P6·Q8 — `seq`·순차 `eventId`가 위치값**이라 두 번째 판을 앞에 끼우면 첫 판이 부분집합이 아니게 된다는 것. 포털이 바이트로 들이는 파일의 성질을 정확히 본 것이다.
- **P8 — 운영 jar로는 바이트 재현이 불가능**(무작위 UUID·시스템 시계·인메모리 시드)하다는 것과, 단계 시계·순차 ID를 **운영 jar 밖 모듈에만** 두는 해법. 시드 SQL과 `standardRules`의 일치를 C8이 증명한다는 구성(S11).
- P9(원천세율이 이미 코드 상수)·P10(가드가 막는 유일한 기존 경로)·P4(기존 `/api/commissions/simulate`는 파이프라인이 아니다)를 **E2 범위 밖 사실로 분리해 기록만** 한 것.

## 3. 포털과 맞물리는 것 (포털 Phase 2 계획 승인과 같은 내용)

- **포털 계약 v1.3 = A-1 채택(⓪a 파일 바이트) + R1~R8 + 피드/명세 응답 설명.** ⓪a 커밋이 push되면 포털 세션이 즉시 만든다(포털 Phase 2 Q13의 "소형 PR"을 이것과 합친다 — 엔진이 따라올 지점을 하나로). 엔진은 **⓪b = `3f876b6`(지금)** → **v1.3 병합 커밋(② 전)** 두 번 올린다.
- 포털은 엔진 E1 `cycle` 스트림(Q11)과 E2 `estimate_cycle` 스트림(Q8)을 시험 자원으로 들인다 — 계약 변경 없음.
- 포털 `recon_result` 키가 `occurredAt`에 기대지 않는다(포털 Q2) — Q9 단계 시계와 무관하게 성립.

## 4. 지시문 측 기록 (`설계고찰.md` §16)

E2 지시문의 문장 17건이 코드와 달랐다(P1~P17) — 그러나 지시문이 결정을 담지 않았으므로 **되돌린 결정은 0건**이다. E1(여덟 건, 되돌림 여럿)과의 차이가 형식 변경의 효과다. 그래도 두 곳은 지시문이 알 수 있었던 것: §4 "세율 하드코딩 금지"(이미 상수였다 — E1 읽기에서 `WithholdingTaxPolicy`를 봤다), ⑤ "digest 고정"(기존 IT가 태그만 쓴다는 것).

## 5. 절차

승인 보관 + 계획 갱신 1커밋 → **⓪a 먼저 push**(해시를 포털에) → ⓪b → ④ → ① → ③ → (포털 v1.3 병합·`UPSTREAM` 재상향) → ② → ⓪ 두 번째 판 + `estimate_cycle` → ⑤ → ⑥(조건부) → 문서·보고서·`e2` 태그·PR. 병합은 수용 심사 뒤.
