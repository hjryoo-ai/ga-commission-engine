# GA 설계사 수수료 계산 시스템 설계서

> 목적: GA(법인보험대리점)에서 설계사 수수료를 계산·지급·환수·정산하는 핵심 시스템의 설계.
> 본 문서는 Claude Code에게 구현을 지시하기 위한 상위 설계 문서이며, 섹션 10의 로드맵 순서대로 구현한다.
> 기술 전제: Java + Spring Boot + Oracle (DB는 교체 가능하도록 SQL 의존 최소화).

---

## 0. 설계의 대전제

이 시스템의 최대 리스크는 기술이 아니라 **규정의 변동성**이다. 금융당국이 감독규정·시행세칙·유권해석을 수시로 바꾸고(1200%룰 GA 확대, 분급제, 비교공시 등), 사규(직급별 지급률, 시책)는 그보다 더 자주 바뀐다. 따라서 설계의 제1원칙은 다음과 같다.

1. **룰은 코드가 아니라 데이터다.** 요율·한도·환수율·지급률은 전부 유효기간(effective date)을 가진 버전 데이터로 관리하고, 계산 엔진은 "기준일에 유효한 버전"을 조회해서 쓴다.
2. **계산 구조가 바뀌는 변경(새 규제 도입 등)은 새로운 계산 Step을 추가하는 방식으로 대응한다.** 기존 Step은 절대 수정하지 않고 버전으로 대체한다.
3. **모든 계산 결과는 불변(immutable)이며, 정정은 취소분개(reversal) + 재계산(rebook)으로만 한다.** 이것이 정확성·감사가능성·재현가능성의 기반이다.
4. **돈 계산은 전부 BigDecimal + 중앙화된 반올림 정책.** double/float 금지.

## 1. 규제 환경 (2026.7 기준) — 설계에 미치는 영향

아래는 금융위원회 「보험 판매수수료 제도 개편」의 시행 로드맵이다. **세부 요율·적용기준은 감독규정/시행세칙/유권해석으로 계속 구체화되므로, 구현 시 수치를 하드코딩하지 말고 반드시 파라미터로 관리할 것.** (최종 확인은 금융위·금감원 원문 기준)

| 시행 시기 | 내용 | 시스템 영향 |
|---|---|---|
| 2021~ | 1200%룰: 초년도 모집수수료 총액 ≤ 월납보험료 × 12배. 전속 채널 및 보험사→GA 지급분에 먼저 적용 | 매출측(보험사→GA) 수수료 검증 |
| 2026.1 | 보험업감독규정 개정 의결 | — |
| 2026.3 | 판매수수료 비교공시 시행, 차익거래 금지기간 확대 | 공시용 데이터 산출 기능 |
| **2026.7.1** | **1200%룰을 GA→소속 설계사 지급분에 개인별 확대 적용** (7/1 이후 체결 계약부터). 모집수수료뿐 아니라 **시책·정착지원금 등 대부분의 지급 항목이 한도에 합산**됨. 대형 GA(설계사 500인 이상)는 수수료 등급·순위 비교설명 의무 | **한도 원장(Limit Ledger) 필수** — 계약×설계사 단위 초년도 누적 지급액 실시간 추적, 지급 전 한도 검증 |
| **2027.1** | **분급제 시행: 초년도 몰아주던 수수료를 4년에 걸쳐 분급** | **분급 스케줄 엔진 필수** — 계약 체결 시점 규정 버전에 따라 지급 커브 생성, 유지 조건 연동 |
| 2029.1 | 분급 기간 7년으로 확대. 유지관리수수료(세부방안 기준 계약체결비용의 월 0.8% 이내, 최대 7년 — 확정 요율은 후속 고시 확인 필요) | 분급 엔진은 "분급 커브 자체를 데이터로" 설계해 4년→7년 확장을 데이터 변경만으로 흡수 |

설계 시사점 요약:

- 한도 룰(1200%)과 분급 룰은 **"계약 체결일 시점의 규정 버전"을 따른다.** 2026.6.30 체결 계약과 2026.7.1 체결 계약은 다른 룰이 적용된다. → 룰 해석기는 항상 기준일(계약일, 회차 도래일 등)을 입력으로 받는다.
- 한도에 "무엇이 포함되는가"(모집수수료/시책/정착지원금/이벤트성 지급...)의 정의 자체가 유권해석에 따라 바뀔 수 있다. → **지급 항목별 '한도 포함 여부' 플래그를 데이터로** 관리한다.
- 규제 우회(변칙 지급)는 당국의 집중 모니터링 대상이므로, 모든 지급 건은 한도 원장에 남고 초과 시도는 차단+로그가 남아야 한다. 이는 컴플라이언스 방어 자료가 된다.

## 2. 도메인 개요

### 2.1 수수료 흐름 (GA의 양면성)

GA는 수수료의 **수취자이자 지급자**다. 두 흐름을 반드시 분리해서 모델링한다.

```
[보험사(원수사) N개] --(EDI/수수료명세)--> [GA: 매출측 수수료(INBOUND)]
                                              |
                                              v  (지급률/시책/한도/분급/환수 적용)
                                         [GA: 비용측 수수료(OUTBOUND)]
                                              |
                                              v
                              [설계사 개인 + 조직(팀장/지점장/본부) 오버라이드]
```

- **매출측(INBOUND)**: 보험사가 GA에 지급하는 수수료. 보험사마다 상품·요율·명세 포맷이 전부 다르다. 자체 계산치와 보험사 명세를 **대사(reconciliation)** 해야 한다.
- **비용측(OUTBOUND)**: GA가 설계사에게 지급하는 수수료. 1200%룰(2026.7~)과 분급제(2027.1~)가 직접 적용되는 영역. 본 시스템의 핵심.
- 두 흐름의 차이가 GA의 마진이며, 계약·설계사·상품 단위 마진 분석이 가능해야 한다.

### 2.2 수수료 유형 (OUTBOUND 기준)

| 유형 | 코드 예시 | 설명 | 1200% 한도 포함 |
|---|---|---|---|
| 초년도 모집수수료 | `FY_COMM` | 신계약 체결에 따른 수수료. 회차(1~12회차)별 요율 존재 | 포함 |
| 계속(유지)수수료 | `RENEWAL` | 2차년도 이후 계속보험료 입금 시 | 미포함(초년도 아님) |
| 시책/프로모션 | `INCENTIVE` | 기간·상품·실적 조건부 인센티브 | **포함(2026.7~)** |
| 정착지원금 | `SETTLEMENT_SUPPORT` | 설계사 영입/정착 지원 | **포함(2026.7~)** |
| 오버라이드(조직수수료) | `OVERRIDE` | 팀장/지점장/본부장 등 상위 조직 지급분 | 적용 기준 확인 필요 → 플래그로 관리 |
| 분급 수수료 | `DEFERRED` | 2027.1~ 분급 스케줄에 따른 이연 지급분 | 스케줄 자체가 한도의 산출물 |
| 유지관리수수료 | `MAINTENANCE` | 2029 로드맵. 유지율 연동 | 미포함 예상, 고시 확인 |
| 환수 | `CLAWBACK` | 해약/실효/철회/미유지 시 회수 (음수 지급) | 한도 원장에서 차감 |

한도 포함 여부는 하드코딩하지 말고 `COMM_TYPE` 마스터의 속성(유효기간 포함)으로 둔다.

### 2.3 수수료 라이프사이클 이벤트

수수료는 스스로 발생하지 않고 **계약 이벤트에서 파생**된다. 이벤트 주도로 설계한다.

| 이벤트 | 수수료 영향 |
|---|---|
| 신계약 체결(청약 승인) | 초년도 수수료 발생, 1200% 한도 원장 개설, (2027~) 분급 스케줄 생성 |
| 회차 보험료 입금 | 회차별 수수료 발생, 분급 조건 충족 체크 |
| 청약철회 | 기지급 수수료 전액 환수 |
| 해약/실효 | 환수율 테이블에 따른 환수, 분급 스케줄 중단 |
| 부활 | 수수료/스케줄 재개 (환수분 재지급 여부는 사규) |
| 감액/보험료 변경 | 월납보험료 변경 → **1200% 한도액 재산정**, 분급 스케줄 조정 |
| 설계사 이동/해촉 | 잔여 분급·환수 귀속 처리 (고아 수수료 정책) |
| 보험사 정정 명세 수신 | 매출측 정정 → 비용측 재계산 트리거 |

### 2.4 조직·설계사

- 설계사: 위촉코드, 직급/등급(지급률 결정), 위촉일/해촉일, 소속 이력(조직 이동 이력 필수 — 지급 시점 소속 기준인지 계약 시점 소속 기준인지는 사규 파라미터).
- 조직: 트리 구조(본부-지점-팀), 오버라이드 배분율은 계층별 요율 테이블.
- 세무: 설계사는 통상 사업소득자 → 지급 시 3.3% 원천징수(소득세 3% + 지방소득세 0.3%), 지급명세서 산출. (지급 모듈 범위, 세율은 파라미터)

## 3. 핵심 설계 원칙

1. **Effective-Dated + 버전 관리 (이중 시간축 권장)**
   - 모든 룰/요율 레코드는 `apply_from`, `apply_to`(업무 유효기간) + `created_at`, `superseded_at`(시스템 기록기간)을 가진다.
   - 업무 시간축: "이 계약(2026.8.1 체결)에는 어떤 요율이 적용되나" → 기준일로 조회.
   - 시스템 시간축: "지난달 마감 때는 어떤 요율로 계산했나" → 소급 정정·감사 대응. 완전한 bitemporal이 부담이면 최소한 "계산 결과에 사용한 룰 버전 ID를 박제"하는 방식으로 재현성을 확보한다(필수).
2. **불변 원장 + 취소/재분개(Reversal & Rebook)**
   - `COMM_CALC` 레코드는 생성 후 UPDATE 금지(상태 전이 제외). 오류 정정은 원본을 참조하는 음수 reversal 레코드 + 신규 레코드.
   - 마감(월마감) 확정된 기간의 레코드는 절대 불변. 마감 후 발견된 오류는 익월 조정(`ADJUSTMENT`)으로 반영.
3. **결정론적 계산 + 근거 박제**
   - 동일 입력 + 동일 룰 버전 → 항상 동일 출력(멱등). 계산 결과에는 사용된 룰 버전 ID 목록, 입력 스냅샷, 단계별 중간값(trace)을 JSON으로 저장한다. → 감사·민원·당국 검사 대응.
4. **한도는 원장으로, 검증은 지급 전에**
   - 1200% 한도는 사후 리포트가 아니라 **지급 파이프라인의 게이트**다. 초과분은 자동 삭감/이연되고 사유가 기록된다.
5. **도메인 로직의 프레임워크 독립**
   - 계산 엔진(core)은 Spring/Oracle 무의존 순수 Java 모듈로 만들어 단위 테스트를 밀리초 단위로 돌린다. DB·배치는 어댑터.

### 3.1 룰 관리 전략: 하이브리드 (범용 룰엔진 비권장)

Drools 같은 범용 룰엔진은 이 도메인에서 디버깅·감사·성능·학습비용 문제가 크다. 대신 3계층 하이브리드를 권장한다.

| 계층 | 관리 방식 | 예시 | 변경 시 배포 필요 |
|---|---|---|---|
| 요율·파라미터 | DB 테이블 (유효기간+버전) | 회차별 요율, 지급률, 환수율, 한도 배수(12배), 분급 커브 | 아니오 |
| 조건식 | 제한된 표현식(선택적, SpEL 등) 또는 설정 플래그 | "한도 포함 여부", "부활 시 재지급 여부" | 아니오 |
| 계산 구조 | 버전이 붙은 코드 Step (전략 패턴) | 1200% 한도 로직 자체, 분급 알고리즘 | 예 (신규 Step 추가) |

새 규제가 나오면: ① 파라미터로 흡수 가능한가 → 테이블 등록으로 끝. ② 새 계산 단계가 필요한가 → 새 `CalculationStep` 구현 + 유효기간 등록. 기존 코드는 건드리지 않는다.

## 4. 시스템 아키텍처

### 4.1 모듈 구성 (Gradle 멀티모듈)

```
commission-system/
├── commission-domain      # 순수 도메인: Money, Rate, Policy, Agent, 이벤트, 값객체 (의존성 없음)
├── commission-rule        # 룰 저장/해석: RuleRepository, effective-date 버전 해석기
├── commission-calc        # 계산 엔진: 파이프라인, CalculationStep 구현체들
├── commission-limit       # 1200% 한도 원장/검증
├── commission-deferral    # 분급 스케줄 생성/집행 (2027 대비)
├── commission-clawback    # 환수 엔진
├── commission-inbound     # 보험사 EDI/명세 수신·정규화 (보험사별 어댑터)
├── commission-recon       # 매출측 대사(보험사 명세 vs 자체 계산)
├── commission-settlement  # 월마감/지급/원천세/조정
├── commission-batch       # Spring Batch 잡 (마감 배치, 분급 배치, 환수 배치)
├── commission-api         # REST API (조회, 시뮬레이션, 관리자 요율 등록)
└── commission-infra       # Oracle 어댑터 (MyBatis 매퍼), 공통 인프라
```

의존 방향: `api/batch → calc/limit/... → rule → domain`. domain은 아무것도 의존하지 않는다.

### 4.2 계산 파이프라인

계산 단위는 `(계약이벤트 × 수급자)`. 하나의 이벤트가 설계사 본인 + 조직 오버라이드 수급자 여러 명의 계산을 낳는다.

```
PolicyEvent 수신
  → [1] 검증/정규화 (보험사별 어댑터, 중복 이벤트 멱등 처리: 이벤트 natural key)
  → [2] 수급자 결정 (설계사 + 오버라이드 체인, 기준: 사규 파라미터)
  → [3] 룰 해석 (기준일로 요율/지급률/한도룰/분급룰/환수룰 버전 확정 → RuleSnapshot)
  → [4] 계산 Step 체인 실행:
        BaseCommissionStep      기본 수수료 = 산출기준액 × 요율
        PayoutRateStep          직급/등급 지급률 적용
        IncentiveStep           시책 계산 (조건 충족 검증)
        LimitGateStep           ★ 1200% 한도 검증/삭감/이연
        DeferralSplitStep       ★ 분급 스케줄 분할 (2027.1~ 유효)
        ClawbackOffsetStep      기존 환수 채권과 상계
        WithholdingTaxStep      원천세 (지급 단계에서 수행해도 됨)
  → [5] 결과 저장 (COMM_CALC + trace + 사용 룰버전) — 상태 CALCULATED
  → [6] 월마감 배치에서 확정(CONFIRMED) → 지급(PAID)
```

각 Step은 아래 인터페이스를 구현하며, **Step 목록 자체도 유효기간을 가진 설정**이다(예: `DeferralSplitStep`은 2027-01-01부터 활성).

## 6. 핵심 엔진 상세

### 6.1 1200% 한도 엔진 (LimitGateStep)

1. 대상 판정: 계약 체결일로 `LimitRule` 버전 조회. GA→설계사 적용은 2026-07-01 이후 체결 계약(그 이전 계약은 미적용) — 이 분기 자체가 룰 데이터다.
2. 원장 조회/생성: `(policy_no, agent_id)` 로 `LIMIT_LEDGER` 확보. `limit_amount = monthly_premium × limit_multiple`.
3. 합산 대상 판정: 이번 계산 라인 중 `COMM_TYPE_MST.limit_included='Y'`(기준일 유효 버전) 항목만 합산.
4. 게이트: `available = limit_amount − accum_paid`.
   - `calc_amount ≤ available` → 통과, 원장 가산.
   - 초과 → 정책 파라미터에 따라 ① 초과분 삭감(CUT) 또는 ② 초년도 종료 후 이연(DEFER_AFTER_FY). 어느 쪽이든 `limit_cut_amt`와 사유를 기록. **기본값은 규정 위반 방지 관점에서 지급 차단 + 이연 스케줄 생성 권장.**
5. 재산정 트리거: 보험료 감액/증액 이벤트 → `monthly_premium` 갱신 및 한도 재계산 → 기지급 누적이 신한도 초과 시 처리 정책(환수 vs 향후지급 중단)은 유권해석 확인 필요 → 파라미터.
6. 동시성: 원장 가산은 `SELECT ... FOR UPDATE` 또는 낙관적 락으로 직렬화. 지급 트랜잭션과 원장 갱신은 동일 트랜잭션.

불변식(테스트로 상시 검증): **어떤 시점에도 `accum_paid ≤ limit_amount`**, `accum_paid = Σ LIMIT_LEDGER_DTL.amount`.

### 6.2 분급 엔진 (2027.1 대비 — 구조만 먼저 구현)

- 분급 커브를 데이터로: `DEFERRAL_CURVE(curve_id, apply_from, apply_to)` + `DEFERRAL_CURVE_DTL(curve_id, year_no or month_no, pct)`. 2027 커브(4년), 2029 커브(7년)를 레코드로만 추가.
- 신계약 계산 시 `DeferralSplitStep`이 초년도 지급분/이연분을 분할하고 `DEFERRAL_SCHEDULE` 생성.
- 월 배치가 도래분(`due_ym = 당월`) 중 `pay_condition` 충족 건을 RELEASED로 전환해 지급 파이프라인에 투입. 해약/실효 이벤트는 잔여 스케줄 CANCELLED.
- 세부 요율(유지관리수수료 월 0.8% 등)은 고시 확정 전이므로 **커브 데이터 등록만으로 대응 가능해야 한다**는 것이 이 모듈의 완성 기준.

### 6.3 환수 엔진

- 트리거: CANCEL/LAPSE/WITHDRAW/REDUCE 이벤트.
- 환수액 = 기지급 수수료(환수 대상 유형만) × 경과 회차 구간별 환수율(`CLAWBACK_RULE`, 계약일 기준 버전).
- 환수는 음수 `COMM_CALC` 로 생성 → 당월 지급액과 상계 → 부족분은 `CLAWBACK_RECEIVABLE` 채권화 → 이후 지급에서 자동 상계. 해촉자 채권은 별도 회수 프로세스(범위 외, 데이터만 제공).
- 환수 발생 시 `LIMIT_LEDGER.accum_paid` 차감(초년도 윈도우 내인 경우) — 한도 여유가 다시 생기는지 여부도 유권해석 확인 대상 → 파라미터.

### 6.4 정정·재계산 (Reversal & Rebook)

- 입력 오류/보험사 정정 명세/룰 소급 변경 시: 대상 `COMM_CALC` 상태를 REVERSED로 전이 + 음수 reversal 레코드 생성(원본 참조) + 새 룰로 재계산 레코드 생성.
- 미마감월 건은 당월 내 정정, 마감월 건은 `ADJUSTMENT`로 익월 귀속. **과거 마감 숫자는 절대 바뀌지 않는다.**
- 재계산 배치는 멱등: 같은 요청을 두 번 돌려도 결과 동일(reversal 중복 생성 방지 키).

## 7. 마감·지급·대사 프로세스 (월 주기)

```
D-5~D-1  INBOUND 명세 수신 마감 → 대사 배치 (자체계산 vs 보험사 명세, 차이 리포트/보류 처리)
D-Day    월마감 배치:
         ① 당월 이벤트 계산 완료 확인 (미처리 PENDING 0건)
         ② 분급 도래분 RELEASE
         ③ 환수/채권 상계
         ④ 1200% 한도 전수 검증 리포트 (불변식 위반 0건 확인)
         ⑤ CALCULATED → CONFIRMED 확정, SETTLE_CLOSE = CLOSED
D+1~     지급 배치: 원천세 계산 → 이체 파일 생성 → PAID 전이 → 지급명세서 데이터
```

- 마감은 체크리스트가 전부 통과해야 CLOSED로 전이(강제 마감은 권한+사유 기록).
- 대사 차이는 유형화(요율 차이/누락/타이밍 차이)해서 관리 화면에 노출 — GA 실무에서 매출 손실 방지의 핵심 기능.

## 8. 정확성 보장·테스트 전략

1. **골든 테스트셋**: 정산 담당자가 엑셀로 검증한 대표 케이스(상품×이벤트×경계값)를 리포지토리에 CSV/엑셀로 두고, 계산 엔진 결과와 자동 비교하는 테스트를 CI에 상시 편성. 규정 변경 때마다 케이스 추가. (최소 케이스 축: 신계약/회차입금/철회/13회차 전후 해약/감액/부활 × 한도 임박/초과 × 분급 전후 계약)
2. **불변식 테스트(property-based, jqwik 등)**: 한도 초과 절대 불가, reversal 합계 = 원본 합계 × −1, 분급 스케줄 합 = 이연 원금, 재계산 멱등성.
3. **경계값**: 초년도 윈도우 경계일, 요율 apply_from 당일, 2026-06-30 vs 07-01 체결 계약, 월납보험료 변경 직후.
4. **반올림 회귀 테스트**: 반올림 정책 변경은 금액 차이 diff 리포트를 산출하는 전용 테스트로만 반영.
5. **섀도 런**: 기존 시스템(또는 수기 정산)이 있다면 1~2개 마감 주기 병행 계산 후 전수 비교하고 전환.
6. **감사 재현**: 임의 `calc_id` 하나를 주면 룰 버전+입력 스냅샷으로 동일 금액을 재산출하는 replay 기능을 테스트로 보증.

## 10. 구현 로드맵 (Claude Code 작업 순서)

각 Phase는 독립적으로 머지 가능해야 하며, Phase마다 골든 테스트를 함께 작성한다.

- **Phase 0 — 골격**: Gradle 멀티모듈 구성, `Money`/`RoundingPolicy`/기본 값객체, Flyway 초기 스키마(섹션 5), Testcontainers 기반 테스트 하네스. *완료 기준: Money 산술·반올림 단위테스트 통과.*
- **Phase 1 — 룰 저장소**: effective-dated 조회(`RuleRepository`), 요율/지급률/COMM_TYPE 마스터 CRUD + 승인 상태 전이, "기준일 조회만 허용" 규약. *완료 기준: 유효기간 경계·버전 교체 테스트 통과.*
- **Phase 2 — 기본 계산 파이프라인**: `POLICY_EVENT` 수신(멱등키), 수급자 결정, Base+Payout Step, `COMM_CALC` 저장(trace·룰버전 박제), 오버라이드 배분. *완료 기준: 신계약/회차입금 골든 케이스 통과.*
- **Phase 3 — 1200% 한도 엔진**: `LIMIT_LEDGER`+DTL, `LimitGateStep`, 감액 재산정, 동시성 처리, 불변식 property 테스트. *완료 기준: 2026-06-30/07-01 경계 케이스, 한도 임박·초과·환수 후 복원 케이스 통과.*
- **Phase 4 — 환수 엔진**: 환수율 테이블, 음수 계산, 채권화·상계, 한도 원장 차감. *완료 기준: 13회차 전후 해약·철회·부활 골든 케이스.*
- **Phase 5 — 정정/재계산**: Reversal & Rebook, 재계산 배치(멱등), replay 기능. *완료 기준: 소급 요율 변경 시나리오 전체 통과.*
- **Phase 6 — 마감·지급**: Spring Batch 마감 잡(체크리스트 게이트), 지급·원천세, `ADJUSTMENT`. *완료 기준: 마감 후 불변성 테스트(마감월 UPDATE 시도 차단).*
- **Phase 7 — 분급 엔진**: 커브 데이터 모델, `DeferralSplitStep`(2027-01-01 활성), 도래/조건 배치. *완료 기준: 4년 커브를 7년 커브로 데이터만 바꿔 동작.*
- **Phase 8 — INBOUND·대사**: 보험사 어댑터 1개(파일럿) + 정규화 + 대사 리포트. 이후 보험사별 어댑터 증설.
- **Phase 9 — API/관리 기능**: 조회 API, 수수료 시뮬레이션("이 계약 체결 시 초년도 예상 수수료/한도 소진"), 요율 등록 승인 워크플로.

Claude Code에 지시할 때 각 Phase 프롬프트에 반드시 포함할 것: ① 본 설계서 해당 섹션, ② "double 금지, RoundingPolicy 외 반올림 금지, COMM_CALC UPDATE 금지, 룰 조회 시 기준일 필수" 규약, ③ 해당 Phase 골든 케이스 표.

## 11. 미결정 사항 (구현 전 정산·컴플라이언스 담당자 확인 필요)

규정·사규 확인이 필요한 항목이며, 전부 **파라미터로 구현해 어느 답이 와도 코드 수정 없이 반영**되게 한다.

1. 1200% 한도의 "초년도" 정의(체결일 기준 12개월인지, 회차 기준인지)와 월납환산 방식(일시납·연납 계약의 환산 기준).
2. 한도 포함 항목의 정확한 범위(오버라이드 조직수수료, 이벤트성 시상, 교육비 지원 등) — 이행 지원센터/TF 유권해석 추적 필요.
3. 한도 초과분 처리: 삭감 소멸인지, 초년도 이후 이연 지급 가능인지.
4. 감액으로 한도가 기지급액 아래로 내려간 경우의 처리(환수 vs 향후 지급 중단).
5. 환수율 테이블 실값(사규), 부활 시 환수분 재지급 여부, 해촉자 환수 채권 처리 절차.
6. 오버라이드 귀속 기준: 계약 시점 소속 vs 지급 시점 소속, 설계사 이동 시 잔여 분급 귀속.
7. 반올림 정책(원단위 절사/반올림)과 적용 단위(라인별 vs 합계).
8. 2027 분급제의 확정 커브·유지 조건·기존 계약 경과조치(감독규정 확정 고시 확인).
9. 보험사별 INBOUND 명세 포맷 목록과 우선 연동 대상 보험사.
10. 마감 일정(D-Day), 강제 마감 권한 체계, 지급 주기(월 1회/2회).

## 부록 A. 대표 시나리오 워크스루 (골든 케이스 초안)

**시나리오: 2026-08-01 체결, 월납 30만원 계약, 설계사 A(등급 지급률 90%)**

1. 한도 개설: `limit_amount = 300,000 × 12 = 3,600,000원`.
2. 신계약 수수료: 기준액 × 초년도 요율 × 지급률 → 예시로 2,800,000원 산출 시 한도 여유(3,600,000) 내 → 지급, `accum_paid = 2,800,000`.
3. 시책 1,000,000원 발생 → 한도 잔여 800,000원 → **200,000원 초과** → 800,000원만 지급, 200,000원은 정책에 따라 삭감 또는 초년도 이후 이연 + 사유 기록.
4. 7회차 납입 후 해약 → 환수율 테이블 적용 구간 조회 → 환수액 음수 계산 생성, 당월 지급과 상계, `accum_paid` 차감.
5. 감사 요청: `calc_id` replay → 당시 룰 버전으로 동일 금액 재산출 확인.

(금액·요율은 전부 예시값이며 실제 요율은 요율 테이블 등록값을 따른다.)
