# E3.2 정비 지시문 — 엔진 저장소 (v1.0)

## 역할과 맥락

엔진(`ga-engine`) E3.1 수용 후 쌓인 정비 항목 셋을 한 PR로 닫는다. **새 기능은 없다.** Phase 6B 심사가 "6B가 엔진에 새로 요구하는 것은 없다"고 확인했으므로 E4는 열지 않는다. 브랜치 `work/e3.2`, 태그 `e3.2`, 병합은 수용 심사 회신 뒤.

## 작업 목록

1. **마이그레이션 번호 전역 단조 문서화.** 엔진 마이그레이션의 번호 체계(현재 V10x 대)가 왜 그 번호에서 시작하고 어떤 규칙으로 늘어나는지, 번호 재사용 금지와 "커밋된 마이그레이션은 고치지 않는다"(ga-disclosure와 같은 원칙)를 `docs/db-migrations.md`에 적는다. 테스트: 마이그레이션 파일명이 단조 증가하고 빈 번호가 없음을 단언(있으면 그 이유를 문서에).
2. **V104 `product_key` 폭 40.** 계약 패턴 `^[A-Z0-9][A-Z0-9-]{0,7}:[A-Za-z0-9][A-Za-z0-9._-]{0,30}$`의 최대 길이는 40이다. 컬럼 폭을 40으로 넓히고(좁히지 않는다), 경계 테스트(길이 40 통과·41 거부)를 계약 테스트와 DB 양쪽에. 기존 행은 모두 ≤ 40이므로 데이터 변환 없음(마이그레이션이 단언).
3. **엔진 계약 `format` → `pattern`.** `engine-disclosure.openapi.yaml`과 등급 스냅샷 스키마의 `format:`을 전부 `pattern`으로(날짜·UUID·해시). 소비 측(ga-disclosure)이 쓰는 검증기가 `format`을 단언하지 않는다는 것이 이유다(6A D14). **공유 계약이므로 양쪽을 맞춘다**: 엔진 PR 병합 커밋 뒤 ga-disclosure의 `contracts/engine/...` 사본·`CHECKSUMS`·`UPSTREAM`(병합 커밋 가리킴)을 갱신하는 후속 커밋을 ga-disclosure `main`에 낸다(그쪽 CI 통과 확인). 의미 변경이 아니라 표기 변경이므로 바이트 동일성 검사 외에 요청·응답 예시가 양쪽에서 통과함을 확인.
4. **CLAUDE.md 정합성 확인.** 엔진 저장소 CLAUDE.md에 ga-disclosure와 같은 규약이 있는지 확인하고 없으면 추가: jqwik 금지(규칙 9 포함), "PR 병합은 수용 심사 회신 뒤에만", 규칙 파일의 사실 정정은 바로·의미 변경은 승인. 이미 있으면 "변경 없음"으로 보고.
5. **의존성 점검.** 락 파일의 외부 의존성(Boot BOM 밖)을 열거하고 OSV 조회 결과를 `docs/third-party.md`에 기록(없으면 생성). 버전 올림은 **하지 않는다** — 취약점이 있으면 보고만.
