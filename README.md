# ga-commission-engine

**GA(법인보험대리점) 설계사 수수료 계산·지급·환수·정산 엔진** — 규제 변동성을 코드가 아닌 데이터로 흡수하도록 설계한 Java/Oracle 시스템.

*A commission calculation engine for Korean insurance GA channels, built to absorb regulatory volatility (the 1200% cap, deferred-payout mandates) as rule data instead of code changes.*

> **면책**: 본 저장소는 학습·포트폴리오 목적입니다. 문서에 등장하는 규제 내용(1200%룰, 분급제, 비교공시 등)은 공개 자료 기반의 예시적 정리이며, 실제 적용 기준은 금융위원회·금융감독원 원문과 유권해석을 따라야 합니다. 모든 요율·금액·수치는 가상의 예시값입니다.

---

## 왜 어려운 문제인가

보험 설계사 수수료는 "단가 × 수량"이 아닙니다.

- **규제가 움직입니다.** 초년도 수수료 총액을 월납보험료의 12배로 제한하는 1200%룰이 2026-07-01부터 GA 소속 설계사 개인별 지급까지 확대됐고(시책·정착지원금 합산), 2027년부터는 분급제(4년), 2029년부터 7년 분급이 예정되어 있습니다. **2026-06-30 체결 계약과 07-01 체결 계약에 서로 다른 룰이 적용**되어야 하고, 세부 기준은 유권해석으로 계속 바뀝니다.
- **돈은 정확해야 하고, 되돌릴 수 있어야 하고, 증명할 수 있어야 합니다.** 해약·철회·감액·부활이 기지급 수수료를 소급해서 흔들고, 마감된 과거 숫자는 불변이어야 하며, 임의의 계산 건은 몇 달 뒤에도 당시 그대로 재현(replay)되어야 합니다.
- **동시성이 돈에 닿습니다.** 같은 계약의 계산 두 건이 경합하면 한도(1200%)를 초과 지급할 수 있습니다 — 사후 리포트가 아니라 지급 전 게이트로 막아야 합니다.

## 핵심 설계 원칙

| 원칙 | 구현 |
|---|---|
| **룰은 코드가 아니라 데이터** | 요율·한도배수·환수율·분급커브 전부 유효기간(effective-dated)+버전 데이터. 룰 조회는 **기준일 필수** — "현재 유효" API 자체가 없음(리플렉션 테스트로 상시 강제). 4년→7년 분급 확장이 커브 레코드 교체만으로 동작함을 테스트로 증명 |
| **불변 원장 + 취소분개** | 계산 결과는 UPDATE 금지. 정정은 reversal & rebook. 순액은 **전 상태 합산**(합산 규약) — 상태 필터 SUM 금지, 공용 컴포넌트 경유만 |
| **판정과 전기는 한 락 안에서** | 1200% 한도 게이트는 `SELECT FOR UPDATE` 획득 → 판정 → 저장 후 훅에서 확정 calcId로 원장 전기 → 커밋까지 단일 직렬화 단위. 실 Oracle 경합 테스트로 `accum ≤ limit` 불변식을 멀티스레드에서 증명 |
| **fail-fast, 침묵 기본값 금지** | 필수 룰 데이터 누락 시 계산 거부. 기준일에 룰이 2건 매칭되면(Ambiguous) 아무거나 고르지 않고 시끄럽게 실패. placeholder 구현은 운영 프로파일에서 **기동 자체가 실패** |
| **감사 재현성** | 계산 결과에 사용 룰버전·입력 스냅샷·단계별 trace 박제. 원장은 단조 증가 전기 순번으로 임의 시점 재구성 → 임의 `calc_id` replay가 테스트로 보증됨 |
| **정밀도** | 금액은 `Money`(BigDecimal 래핑)+중앙 반올림 정책만. double/float 금지, 웹 계층 직렬화까지 정수 고정 |

## 아키텍처

Gradle 멀티모듈 (도메인 코어는 프레임워크 무의존):

```
domain → rule → calc / limit / deferral / clawback → settlement / batch / api / shadow
                                   └── infra (MyBatis + Oracle 어댑터)
```

- **계산 파이프라인**: 이벤트 수신(멱등키) → 수급자 결정 → 기준일 룰 해석 → Step 체인(기본수수료→지급률→시책→**한도 게이트**→**분급 분할**) → 불변 저장 → 저장 후 훅(원장 전기). 신규 규제는 기존 Step 수정이 아니라 **유효기간 붙은 신규 Step 등록**으로 흡수
- **승인 워크플로**: 요율·시책 마스터는 트리밍/SUPERSEDE 버전 교체 + function-based unique index를 최종 심판으로 하는 경합 처리(lock-then-revalidate 재시도) + 저장소 diff에서 자동 도출되는 변경 감사(기록 누락이 구조적으로 불가능)
- **관리자 입력 표현식 샌드박스**: 시책 조건식(SpEL)은 read-only 데이터 바인딩 컨텍스트에서만 평가 — 타입 참조·빈 참조·생성자·메서드 호출 거부를 금지 구문 테스트 20종으로 박제
- **배치**: Spring Batch 5, JobInstance=요청 dedup, 태스크릿+항목 단위 업무 트랜잭션으로 청크×락 충돌 회피 — kill 후 재시작 시 값 멱등성을 실 Oracle로 검증
- **골든셋**: 정산 담당자가 엑셀로 편집하는 자기완결 CSV 번들(케이스=시드+타임라인+기대결과). 신규 케이스가 **코드 변경 0**으로 CI에 편입
- **섀도 런**: 외부 정산 결과와 수급자×유형×마감월 원 단위 대조, 차이를 6유형(TIMING 2-패스 재분류 포함)으로 분류 — go-live 게이트

## 검증 체계 — 테스트 356건

| 계층 | 내용 |
|---|---|
| 계약 테스트 | 인메모리 레퍼런스와 Oracle 어댑터에 **동일 스위트**를 돌려 동작 동등성 증명 (불변 원장·멱등키·전기 순서·빈 문자열=NULL 시맨틱) |
| 동시성 IT (실 Oracle) | 한도 경합 → 정확한 삭감 금액 수렴, 원장 동시 생성 → 유니크 재시도 수렴, 승인 경합 → 래치로 경합 창을 강제로 열어 인덱스 심판 경로 자체를 증명 |
| property (jqwik) | 한도 불변식, reversal 상쇄, 분급 스케줄 합=원금, 재계산 멱등성 |
| 골든셋 CSV | 규정 경계 케이스(06-30/07-01 체결, 13회차 전후 해약, 감액, 마감 전 정정 …) |
| 기동 스모크 E2E | 풀 컨텍스트 부팅 → 마이그레이션 → 계산 → REST → 마감 잡 (Testcontainers `gvenzl/oracle-free`) |
| 공급망 | Gradle dependency verification(sha256) 활성 — 의존성 추가 시 diff 리뷰가 워크플로에 포함 |

**검증 체계가 실제로 잡은 결함들** (출시 전 발견, 전부 회귀 테스트 + 구조적 방지책으로 박제):

1. **정산 이중 차감** — 순액 계산이 상태 필터 SUM을 사용해 마감 전 정정 시 과소 지급되는 잠복 결함. 합산 규약을 공용 컴포넌트(`NetAmountCalculator`)로 구조화해 재발 차단
2. **Oracle NULL 유일성 누수** — nullable 필터 컬럼을 그대로 인덱싱하면 "전체-대상 ACTIVE 중복"이 유일성 검사를 통과. `NVL('*')` 고정으로 해결, DDL 테스트로 박제
3. **승인자 검증 gap** — blank/"system" 거부가 컨트롤러에만 있어 배치·러너 경로가 무방비. 서비스 계층 공용 정책으로 하강(심층 방어)

## 실행

요구사항: JDK 21, Docker (Oracle 통합 테스트용 — `gvenzl/oracle-free` 자동 기동)

```bash
./gradlew build   # 전체: 단위/H2 + 골든셋 + 실 Oracle 통합 + 기동 스모크
```

## 개발 방법론 — AI 에이전트를 공학 규율로 지휘하기

이 저장소는 **사람(오너) + 설계·리뷰 AI(Claude) + 구현 AI(Claude Code)** 의 3자 협업으로, 설계서 1장에서 실행 가능한 앱까지 16개 Phase를 하루에 완주한 기록입니다. 속도의 동력은 AI가 아니라 **프로토콜**이었습니다:

1. **정본 설계서 단일 원본** (`commission-system/docs/설계서.md`) — 모든 Phase가 여기서 출발하고, 완료 시 코드와 같은 커밋으로 갱신(변경 이력 v1.0 → v1.2.1)
2. **Phase 지시 = 참조 섹션 + 코딩 규약 전문 + 완료 기준** — "잘 만들어줘"가 아니라 검증 가능한 계약
3. **완료 보고 = 증거 기반** — 테스트 수가 아니라 "이 시나리오에서 이 값이 나왔다"
4. **수용 심사** — 리뷰에서 나온 지적(락 범위, replay 결정론, 과대 진술 정정 등)은 설계서 패치로 환류
5. **"규약보다 구조"** — 코드리뷰로 지키는 규칙은 언젠가 깨지므로, 가능한 모든 규약을 리플렉션 테스트·아키텍처 테스트·DB 제약·기동 가드로 기계화

Phase별 진행은 git 태그(`phase-12` ~ `phase-16-final`)로 남아 있고, 설계 판단의 근거는 `설계고찰.md`(저장소 루트)에 축적되어 있습니다.

## 상태와 한계

구현 로드맵(Phase 0~16)은 소진됐고 실행 가능한 앱까지 조립됐습니다. 다만 이것은 **운영 시스템이 아니라 운영 직전 단계의 엔진**입니다 — 남은 것은 `commission-system/docs/설계서.md` §12(운영 전환 체크리스트)에 명시되어 있습니다: 규제 세부 기준의 유권해석 확인(전부 파라미터로 흡수되도록 설계됨), 보험사별 수신 어댑터 증설, 섀도 런 실데이터 병행, 실 계약상태 판정 연동(현재 placeholder는 운영 프로파일 기동을 구조적으로 차단) 등.
